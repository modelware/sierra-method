This is the oml-mcp skill, from .claude/skills/oml-mcp:

LOAD TOOL SCHEMAS FIRST
If the OML MCP tool schemas aren't loaded yet, load all of them in one
ToolSearch call before doing anything else.

PLANNING DISCIPLINE
Decide whether the question is about retrieving information, updating
ontologies or verifying them, and follow that workflow.
  - Trust results; don't repeat. Re-run a tool only after a change that
    could alter its answer, such as an oml_update.
  - Batch independent calls. Put several searches, or oml_about on several
    members, in one message.

RETRIEVE CONTEXT WORKFLOW
The usual order is search -> about -> (members or paths if needed) -> sparql.
  1. Search first. Run oml_search with short keywords, not phrases. If it
     finds nothing, try one other keyword. If that also fails, ask the user.
  2. Learn about the members you found. Run oml_about once with all the
     IRIs, using a workspace root as context. This often answers the
     question on its own. (When you plan to write: oml_about can show
     inferred predicates. Only oml_shapes says which predicates can be
     asserted.)
  3. Dig deeper if needed. Don't search again after oml_about. Instead use:
       - oml_paths to find the predicate chains between two IRIs (put an
         instance IRI in the source position).
       - oml_members(ontology, kind) to list every member of a given kind.
       - oml_ontologies(includeImports=true) only when the question is
         about the import structure.
  4. Query precisely with SPARQL. Use oml_sparql with a root ontology as
     context. If a query you expected to return data comes back empty, run
     one probe: SELECT ?s ?p ?o WHERE { ?s <pred> ?o } LIMIT 5. If the
     probe is empty, the predicate IRI is wrong. If it returns rows, the
     query logic is wrong.

UPDATE ONTOLOGIES WORKFLOW
  1. Retrieve context first: the relevant classes, properties and
     instances, plus the ontology each change should go in.
  2. Run oml_shapes on every class you'll create or modify. Its
     sh:targetClass, sh:path and sh:class define what you may write.
     Assert only predicates that match a sh:path.
  3. Put all operations in one atomic oml_update call:
       - Order them createInstance -> required assertions and
         annotations -> cross-links.
       - Always assert the type of each instance you create.
       - Apply routine changes directly. Use preview: true only for
         removals, bulk edits or unfamiliar patterns.
       - When removing, remove the links before the members.
       - With createOntology, set targetFolder to a relative oml folder.
  4. Pitfalls:
       - Don't chain fix-up oml_update calls.
       - Don't create an instance without its type and its required facts
         (sh:minCount >= 1).
       - Never edit .oml files directly.
       - Never use addImport on a description ontology; it is only allowed
         on a description bundle.
  5. If oml_update reports lint problems, fix them with a new oml_update.
  6. Once it's lint-free, run these together: oml_validate(only: true) and
     oml_reason(only: true, explanation: false).
  7. If oml_reason returns inconsistent, run it again with
     explanation: true. The highlight field names the conflicting axioms;
     fix the cause with a new oml_update.
